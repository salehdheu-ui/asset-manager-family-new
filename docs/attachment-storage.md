# تخزين مرفقات منصة family

## الوضع الحالي

تدعم المنصة وضعين للتخزين. الوضع الافتراضي هو `database` للمحافظة على تشغيل البيئات الحالية؛ وفيه تُحفظ المرفقات الجديدة بصيغة Base64 في عمود `content`. الوضع الموصى به للإنتاج هو `s3`، وفيه تُحفظ bytes في Object Storage ويُحفظ في قاعدة البيانات `storageKey` وبيانات الملف فقط.

## متغيرات البيئة

```env
ATTACHMENT_STORAGE_MODE=s3
ATTACHMENT_S3_BUCKET=family-attachments
ATTACHMENT_S3_REGION=us-east-1
# اختياري لمزود متوافق مع S3 أو MinIO
ATTACHMENT_S3_ENDPOINT=https://s3.example.com
ATTACHMENT_S3_FORCE_PATH_STYLE=false
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
```

لا تُضاف القيم السرية إلى GitHub. يعتمد `@aws-sdk/client-s3` على متغيرات AWS القياسية أو على آلية الاعتماد التي يوفرها بيئة التشغيل.

## تطبيق المخطط

قبل تشغيل التطبيق بوضع `s3`، طبّق الملف:

```text
migrations/0001_attachment_object_storage.sql
```

يضيف الملف `storage_key` و`storage_url` ويجعل `content` اختياريًا. وهو قابل لإعادة التشغيل بسبب استخدام `IF NOT EXISTS`.

## الترحيل التدريجي

المرفقات القديمة التي لا تملك `storageKey` تستمر في العمل من `content`. المرفقات الجديدة تُرفع إلى Object Storage عند تفعيل الوضع `s3`. بعد التأكد من نجاح النسخ الاحتياطي والتنزيل لكل الملفات، يمكن بناء مهمة مستقلة لترحيل الصفوف القديمة إلى Object Storage ثم تنظيف `content` من قاعدة البيانات.

نسخ النظام الاحتياطية لا تكرر bytes للصفوف التي تملك `storageKey`، لكنها تحتفظ بـ `content` للصفوف القديمة حتى لا تُفقد الملفات أثناء الانتقال.

## ملاحظات تشغيلية

الوصول إلى الملف يمر عبر تفويض المورد نفسه قبل طلب bytes من Object Storage. لذلك لا يكفي امتلاك رابط أو مفتاح التخزين للوصول إلى مرفق عضو آخر. حذف سجل المرفق يحذف المرجع من قاعدة البيانات، بينما يحتاج تنظيف object غير المستخدم إلى سياسة lifecycle لدى مزود التخزين أو مهمة تنظيف لاحقة.
